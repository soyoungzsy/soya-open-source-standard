# 非技术用户可读性标准

## 默认读者

假设读者会打开网页、复制文字和下载文件，但不会编程、不认识终端、不知道 Git、API、部署或目录路径。不让读者先学会开发才能理解项目。中文和英文分别满足，不用直译制造生硬表达。

## 内容顺序

1. 一句话说清：谁在什么情况下，用它做什么，得到什么。
2. 用一个日常输入与结果举例，先展示价值。
3. 写最短开始路径：在哪里打开、点哪个按钮、复制什么、填什么、看到什么。
4. 提前交代需要什么账号、是否收费、哪些内容会交给其他服务。
5. 说明卡住怎么办、如何退出、如何恢复原状、去哪里提问。
6. 原理、命令、文件结构和开发细节放在后面，标为“进阶/给开发者”，普通用户可跳过。

## 用词与操作

- Prompt 首次写成“可复制给 AI 的一段指令”；Skill 写成“让 AI 按固定步骤做事的说明包”。Release 是“可下载的固定版本”，PR 是“等待审查的修改提案”。中文不以英文缩写代替解释，英文也不用开发者黑话。
- “闭环、赋能、上下文、路由、编排、端到端、幂等”等词不能承担核心功能说明，改为具体动作；有必要保留时紧邻解释。
- 不只写“克隆仓库、安装依赖、配置密钥、部署”。默认给点选下载步骤；不得把文件路径当作足够的安装教程。必须用命令时，解释打开哪个工具、复制到哪里、执行几次、预期画面与错误处理。
- 一次只给一个推荐入口。可选方法随后说明；不要先给多个工具选择题。无可用在线入口或一键安装时直说，给真实可行的替代办法，不用一个 Prompt 冒充完整应用。
- 示例不能要求私人材料。使用虚构学习记录、公开网页、虚构植物等。重要操作前说清对数据/页面的影响与恢复办法。
- 所有对外文档都按其明确读者写清用途。开发文档可保留精确术语，但开头说明适合谁、是否可以跳过，并解释项目特有名词。PR 用普通话说明问题、修改后结果、检查与剩余问题。

## 验收：不能靠“已经写得简单”自评

只看公开页面，模拟不会编程的首次访问者，逐项给出页面依据：

| 问题 | 通过标准 |
| --- | --- |
| 这是什么？ | 30 秒内能复述具体用途，不依赖术语 |
| 适合我吗？ | 看得见日常场景、例子和不适用范围 |
| 第一步呢？ | 一个明确入口，不需猜按钮、软件或路径 |
| 怎么知道做对？ | 有具体预期结果和失败后的下一步 |
| 需要花钱/交数据吗？ | 开始前能看到费用、账号与数据去向 |
| 不会装怎么办？ | 有诚实的替代路径或明确的功能限制 |

中文和英文逐项记录“通过/不通过/未验证”及依据。任何阻碍理解或首次操作的问题都必须修订并复查；没有真实用户参与时，写明是 AI 模拟非技术读者自检，不能宣称真实新手测试通过。代码功能、公司授权与安全检查另行完成，不以可读性代替。
